# Partner scheduled trip filters

The Scheduled Trips table defaults to today's departure date in Manila time, All times, All origins and All destinations. The four controls sit in the table header and wrap on smaller screens. Changing any value immediately requests page 1 and updates the table inside the mounted microfrontend; there is no filter button. Departure time offers only hourly buckets containing trips on the selected Manila date, with AM/PM labels. Choosing 7:00 AM matches departures from 7:00:00 AM up to, but excluding, 8:00:00 AM in Manila. Origin and Destination offer only their respective route terminals used on that date. Selecting an All option clears only that filter. Filters are retained in the URL, pagination links and live-update requests. No trips found indicates that no schedules match the combined filters.

GET /api/partner/scheduled-trips accepts date (YYYY-MM-DD), time (optional HH:00 in 24-hour format), originTerminalId and destinationTerminalId (optional GUIDs), page and pageSize. An omitted date defaults to the current Manila date on the server. Past dates are allowed for browsing historical schedules. The selected day or hour is converted to an inclusive-start, exclusive-end UTC interval using Manila's UTC+08:00 offset. Date/time and endpoint predicates run before the database count and pagination. Trips are sorted by departure time, then ID. The former combined terminalId filter is no longer used.

GET /api/partner/scheduled-trips/filter-options accepts date (YYYY-MM-DD, defaulting to today in Manila) and returns distinct, sorted times (HH:00), origins and destinations. All choices come from the full set of visible trips on that date, before pagination and independently of the other dropdown selections. Terminals include their IDs, names, locations and partner names. Inactive terminals are included when referenced by that date's records. The endpoint requires scheduled-trip.read, without requiring scheduled-trip.write or terminal.read, and enforces current active membership of approved partners. Invalid dates return HTTP 400; a date without trips returns three empty arrays. Responses are not cached.

The frontend reloads options when the date changes or scheduled-trip live updates arrive. Requests for previous dates or identities are cancelled. Selections still present in the new choices are preserved; unavailable selections are cleared and pagination returns to page 1. If there are no trips, only the three All options remain. Neither pagination nor selecting a time/endpoint reloads the date's choices. Filter choice failures disable the dropdowns and expose a retry without a page reload. No migration is required.
